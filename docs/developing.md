# Developing nixlab

How nixlab is put together as a codebase, and how to add to it: a catalog app, a setting, a platform service, a command. For pull request etiquette and code style, see [CONTRIBUTING.md](https://github.com/thatbagu/nixlab/blob/main/CONTRIBUTING.md); for the tests, [Testing & CI](./testing.md); for how the running system fits together, [Architecture](./architecture.md).

## Getting set up

You need Nix with flakes, nothing else:

```bash
git clone https://github.com/thatbagu/nixlab && cd nixlab
nix flake show                                   # the outputs, without errors
nix build -L .#checks.x86_64-linux.features      # one fast check
```

To try a change against a real lab, point the lab's input at your checkout:

```bash
cd myinfra
nix flake check --override-input nixlab path:/path/to/nixlab
nixlab render                                    # in the lab's dev shell: the manifests, with your nixlab
```

## The repository

| Path | What's there |
|---|---|
| `flake.nix` | `lib.mkFlake`, `lib.mkNixlab`, `lib.mkTools`, the template, the checks |
| `system/` | what runs on the nodes (k3s, disks, impermanence, SOPS, encryption, upgrades, NAS, power, Tailscale, the tunnel, and the native gateway, VPN, monitoring and apps), and `mk-nixlab.nix` / `mk-flake.nix`, which assemble a lab |
| `system/k8s/` | the Kubernetes side, as nixidy modules: the platform (`services/`), the built-in apps (`apps/`), the app helpers (`lib.nix`), the catalog's wiring, the GitOps engines, network stacks and gateways, the pinned charts (`charts/`) |
| `system/vars/` | the typed `vars.nix` settings (`options.nix`) and the Settings Reference generator |
| `system/cli.nix` | the `nixlab` command itself (help, and the command list for the docs) |
| `catalog/` | the app catalog: one data file per app, and the page generator |
| `tools/` | the `nixlab` commands (one `writeShellApplication` each) and `nixlab.sh` |
| `template/` | the starter lab repo users get from `nix flake init` |
| `tests/` | everything `nix flake check` runs |
| `docs/` | this site (mdBook) |

A lab is assembled in one place: `system/mk-nixlab.nix` evaluates the user's settings against `system/vars/`, then builds every node from `system/node.nix` and the modules next to it, and the Kubernetes render from `system/k8s/` plus the user's `apps/`. Settings reach every module as arguments, never by importing a file.

**The rule for new code:** logic lives in Nix. A script that has to exist (a tool, a systemd unit, a test step) is generated by Nix and shellchecked at build time; don't add new hand-written shell or Python files.

## Adding a setting

1. Declare it in `system/vars/options.nix` with its type, default and a `description` written for someone who doesn't know Nix. Defaults that follow other settings use `defaultText`.
2. Read it where it's used. Kubernetes modules get derived values from `system/k8s/vars.nix` (`vars.features.*` for what's on); NixOS modules get the typed settings.
3. If a combination can't work, add an assertion with a message that says what to do, and a case in the `validation` check.
4. Add a test configuration in `tests/default.nix` that turns it on: it gets evaluation and render checks for free. Then a few assertions in `features`.
5. Regenerate the Settings Reference (a check fails until you do):

   ```bash
   rm -r docs/options && cp -r "$(nix build --print-out-paths .#options-doc)" docs/options && chmod -R u+w docs/options
   ```

6. Document it on the page for its topic (and in `template/vars.nix` if most users should see it).

## Adding an app to the catalog

A catalog app is one file, `catalog/<name>.nix`: its metadata, and its module, a `nixlab.app` call. Catalog apps run natively (`runtime = "native"`), from their NixOS module where nixpkgs has a good one, else their image under Podman, so they work with or without Kubernetes.

```nix
# catalog/vaultwarden.nix
{
  meta = {
    category = "Security";
    description = "Password manager, compatible with the Bitwarden apps.";
    homepage = "https://github.com/dani-garcia/vaultwarden";
    port = 8222;
    health = "/alive";                       # answers when it's up: status page and tests
    settings.signups = "Let new accounts sign up (default true).";   # its own settings
  };
  module = { nixlab, app, ... }: nixlab.app {  # app: its settings, defaults filled in (host, node, signups)
    name = "vaultwarden";
    inherit (app) host node;
    port = 8222;
    runtime = "native";
    state = { "/var/lib/vaultwarden" = "1Gi"; };   # kept, backed up
    healthcheck = "/alive";
    nixos.services.vaultwarden = {
      enable = true;
      config = { DOMAIN = "https://${app.host}"; ROCKET_ADDRESS = "0.0.0.0"; ROCKET_PORT = 8222; SIGNUPS_ALLOWED = app.signups or true; };
    };
  };
}
```

- **Values are defaults:** the user's `apps.<name>.nixos` is merged over the entry's NixOS settings, so write them plainly.
- **The wiring** (settings, unknown names refused) is `system/k8s/catalog.nix`; the settings' types are in `system/vars/options.nix` (`apps`).
- **Test it:** add it to a `vm-catalog-*` test's `apps` list in `tests/default.nix` (it comes up, answers over HTTPS through the gateway, and again after a restart). The `catalog` check verifies every entry is complete.
- **Regenerate the page:** `nix build .#checks.x86_64-linux.catalog-reference -o result && cp result docs/catalog.md`.

## Adding a platform service

Platform services are nixidy modules in `system/k8s/services/<area>/`, imported in `system/k8s/nixidy.nix`:

- Pin its chart in `system/k8s/charts/<repo>/<chart>/default.nix` (the first build prints the `chartHash`).
- Put it behind a switch (`vars.features.<name>`), so it can be turned off and its secrets aren't generated when it is.
- Give it a `syncWave` that fits the [order](./app-modules.md#sync-waves).
- Declare its Secrets in `system/k8s/secrets.nix` and where each value comes from in `secret-values.nix`; `nixlab secrets sync` then generates or asks for them.
- If it needs state on the nodes, add the paths to `system/impermanence/`.
- New images must be in `tests/vm/images.json` for the VM tests (they have no internet): `nix run .#update -- vm-images` regenerates it.

Where nixlab offers alternatives (GitOps engine, network stack, gateway), each implements the same interface in its own directory, and a test checks every implementation provides all of it: see [Architecture: Choices behind one interface](./architecture.md#choices-behind-one-interface).

## Adding a command

A command is a `writeShellApplication` in `tools/<name>.nix`, made with `mkTool` in `tools/default.nix` (which checks it runs from a lab's root), and listed there with its `usage`, a one-line `about` and optional `details`. That one list makes `nixlab help`, `nixlab <command> --help` and the [Command line](./cli.md) page. Regenerate the page:

```bash
nix build .#checks.x86_64-linux.cli-reference -o result && cp result docs/cli.md
```

Tools run for real in the build sandbox in `tests/tools.nix` (no network, a throwaway `$HOME`, a fresh copy of the template): add a case there.

## The docs

The site is [mdBook](https://rust-lang.github.io/mdBook/), built and published by `.github/workflows/docs.yml` on every push to `main` that touches `docs/`. Preview it locally:

```bash
nix shell nixpkgs#mdbook nixpkgs#mdbook-mermaid --command mdbook serve docs
```

- **Two levels:** the Guide is for running a lab (what to type, what you get); Advanced is for changing nixlab or understanding it (how it works, every option). A topic often has a page in each, at its own depth: link across rather than mixing the two on one page.
- **Generated pages** (`cli.md`, `catalog.md`, `options/`) say so in their first lines, with the command that regenerates them. A check fails when they're out of date.
- **Procedures go into tools.** If a page needs several manual steps, that's a missing command or option: write the tool, and keep the page short.
- Keep page file names stable: code, error messages and other sites link to them.
